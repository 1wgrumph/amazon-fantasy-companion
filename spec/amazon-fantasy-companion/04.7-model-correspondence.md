### 4.7 Model correspondence

Text and diagrams preserve the native model’s scope and explicitly identify refinements.

The four packages are self-contained; cross-package linkage is by documented element names and the allocation companion, not formal imported flow bindings. `AFCData` imports `ScalarValues` for its primitive types. The ST-3d receipt closes the earlier parser-unavailable gap; it does not validate wire contracts or real-device behavior.

AlertLifecycle follows detected → matched → gated → emitted → delivered, with matched → suppressed and emitted/delivered → corrected. The retained PanelMode model starts in modeB and transitions only to modeA on spikeFailed. Its Mode A sample-footage meaning is superseded by SD-035 and retained pending Phase 2 design, along with `tvApp.player` and PLAYER. The current fallback is the full-screen companion-app panel in 4.1.12; the old transition is not an implementation instruction. DeviceLink starts unlinked, requests codePending, then links on userConfirm or expires on codeTimeout; expired can request again. Sections 4.1.5, 4.1.10 and 4.1.12 draw these separately.

Identity/revision envelopes, JSON typing, authorization/error handling and API operation signatures are D1 refinements of the named interfaces. They do not amend native models or claim model conformance beyond the recorded parse. The model also predates the persistent manual preset choice in AFC-PR-066; PROFILE and LINEUP allocation comes from the amended register pending model alignment. Model omissions such as cancellation, account unlink/revocation lifecycle and transport tuning remain Phase 2 contract work, not silently completed state transitions.

Correspondence is checked by comparing names, transitions and allocation links with the unchanged model files. AFC-PR-047 and AFC-PR-066 make the known version differences visible, preserving the model evidence while keeping the amended register authoritative.
